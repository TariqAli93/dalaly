# Iraqi office agreements, wording and procedure follow-up

Contract data, legal wording and visual design remain separate. `contract_templates` contains visual settings only (`body={{document}}`); its existing ids are preserved. Six sale and six rental designs consume the same structured document through `renderVisual`. People stay reusable; party roles belong to each contract. Rental assets and images remain separate from sale properties.

## Approval and publication

Every edit appends a complete revision to the existing `legal_contract_templates` / `legal_contract_clauses` tables. Wording, ordering, scope, legal references and approval evidence cannot be overwritten. `legal_content_events` records the actor, reason, parent, reviewed baseline, classification, publication, defaults, scheduling and soft-deletion changes.

The table displays enabled/disabled state, system/custom category, selected default, version and modification date. Existing approval states remain compatible; `publication_status` distinguishes approval from activation. Only an approved active nondeleted version can serve new contracts. Each custom formula has an independent family, and edits append revisions within that family. Activation archives the older active revision of the same family; multiple custom families may remain active within the same scope. A partial unique index allows one active revision per family and another enforces one selected default per contract type. Defaults apply only when their jurisdiction, transaction and property scope match. If the default is inapplicable, exact-scope active wording takes precedence, then explicitly scoped `all_properties` wording. There is no residential fallback for agricultural or commercial property.

The server compares actual wording with the latest approved revision in the same scope. Unicode NFC and whitespace are normalized; Arabic letters, terms and obligations are not rewritten. Clause codes, titles, required flags, conditions and effective order are part of the comparison. Metadata such as the template title, deadline and priority are administrative. Dynamic contract values are separate data and do not revise the wording.

- Authorized office managers can approve and publish valid administrative or substantive revisions directly, including from draft. Approval never requires a lawyer record or verified professional eligibility.
- New and changed wording still passes scope, clause, placeholder and required-content validation before publication. Employees can propose and submit revisions; API permissions prevent them from publishing.
- The database protects immutable wording and approval evidence, requires complete wording and an active approving account, and prevents deletion of system/default formulas. Client-supplied approval or system flags are rejected by strict payload schemas.
- Restoring an old version creates a new draft; restoring a system formula creates an independent custom family. It does not overwrite an earlier text or reset history.

Migration 0021 adds the simple office introduction requested by the user for sale and rental agreements, in each supported jurisdiction. These existing-table revisions have `wording_origin=office_standard`, administrative approval without lawyer credentials, and the explicit `all_properties` scope. No existing user text is promoted or overwritten. The wording records the parties' agreed transaction through the office; it does not claim specialist certification or completed official procedures. Authorized office approval is sufficient for substantive edits; there is no lawyer eligibility gate. Ordinary additional transaction conditions are captured as party-agreed data, not modifications of the protected master text.

## Permissions

`legal_content.read` permits viewing wording and previews. `legal_content.propose` lets employees create revisions and submit proposals. `legal_content.manage` permits management and scheduling. `legal_content.publish` permits office approval, activation/deactivation and default selection. `legal_content.approve` remains a compatible office approval permission; professional verification is no longer checked. `legal_content.delete` permits archiving custom nondefault families. Legacy `legal_reviewers` records remain available to backup/history, but qualification fields and qualification APIs have been removed.

Contract creation/editing uses `contracts.manage`, issuance uses `contracts.issue`, cancellation uses `contracts.cancel`, and printing/export uses `contracts.print`. The API checks these permissions independently of visible buttons. Migration 0022 grants issuance/cancellation to existing contract managers, printing to contract readers, and custom-template deletion to legal managers. RBAC seed definitions include the same keys. Existing manager/editor roles retain their previous read/manage/propose boundaries.

## Editor, clauses and follow-up

**العقود ← الصيغ القانونية** has four statistics, Rental/Sales/Clauses/Versions tabs, searchable property/state tables and permission-aware actions. The editor has metadata and ordered clauses on the right, and the shared RTL A4 preview on the left. Reviewed terms are locked by default. Opening them for changes marks the edit for comparison; the server makes the final classification.

The preview provides tabs for raw wording/placeholders, resolved variable values, rendered demo clauses and the final printable A4 document. Trial printing uses the shared native/browser print adapter and PDF export uses the existing adapter. Preview uses all six visuals for the chosen domain and either explicitly labelled demo values or saved real-contract data. It is always marked as an editor draft. Real data must match contract type, jurisdiction and transaction kind, and the property category unless previewing the explicit general office wording. Optional clauses are shown for inspecting the formula; actual contracts still choose only applicable approved optional clauses. Trial free conditions in the editor affect preview only. No script, HTML, SQL or arbitrary variable evaluation is accepted.

The shared variable whitelist rejects unknown or malformed placeholders. Duplicate normalized clause text is reported before approval; no historical legal terms are deleted automatically. The clause library groups identical reviewed terms and reuses their provenance. Revision snapshots deliberately retain their own clause copies so future library changes cannot alter history. JSON import opens a draft in the editor and ignores external approval/publication flags; JSON export excludes local clause references for transfer to another installation.

Requests have a Baghdad-time target and priority. Submission assigns a one-day operational target if none was supplied; authorized managers can adjust it to the nature of the work. These are operational goals, not legal deadlines. The dashboard groups similar pending requests and shows remaining/overdue time. In-app notices are generated on access and refreshed every minute while the app is open. They are deduplicated per user/revision/target/kind: at most an early and an overdue notice for an unchanged target. Read state persists, obsolete/resolved notices disappear, and optional Electron desktop notices group new items with local suppression and rate limiting. The app does not run a background notification service while closed.

The layout uses existing Vuetify controls, Dalaly colors and RTL. Spacing, grouping and progressive disclosure follow the [Fluent 2 layout guidance](https://fluent2.microsoft.design/layout) using the existing 4-pixel spacing system; no second UI framework is added. Windows desktop notices use the app's AppUserModelID; development notification display also depends on Windows shortcut/OS settings as described in [Electron's notification guidance](https://www.electronjs.org/docs/latest/tutorial/notifications#platform-considerations).

## Contract integration and historical records

Selection requires matching contract type, jurisdiction and transaction kind. The selected enabled default takes precedence when applicable, otherwise the exact property category and then an explicit general formula apply. Agricultural land retains metre/dunam data. An older active revision remains usable while a new proposal is pending.

The one-page contract form automatically fills the contract date, selected property owner, amounts and remaining balance, supports inline customer editing, and saves drafts locally immediately and to the API when required data is complete. Its primary action saves and issues, then opens the dedicated contract-review page. Local drafts remain recoverable when server validation or connectivity prevents autosave. For the measured completion segment after entering valid data, the previous wizard needed six mandatory actions (four Next actions, Save draft, then Issue); the primary Save & Issue action now completes that segment in one action, an 83.3% reduction. This measures mandatory workflow controls and does not claim the same reduction for every typing, selection or document-upload interaction.

The six-to-one completion measure applies to both sale and rental forms. A standard sale with existing complete people/documents, a linked owner (or a unique matching name/phone), default sale wording/design and today's date needs six clicks instead of thirteen, a 53.8% reduction: the previous flow used four Next clicks, two each to choose the asset, seller and buyer, one to focus the paid amount, Save draft and Issue. The new flow uses two each for the asset and buyer, one paid-amount focus and Save & Issue. Counts exclude keystrokes, scrolling, optional previews and new people/documents. Rental dates remain explicitly selected; a billing period never invents a tenancy duration.

Issuance checks `contracts.issue`, complete immutable snapshots and current active nondeleted wording; it requires no lawyer eligibility, including additional conditions and older draft models. Optional recorded office reviews remain tied to the saved hash and draft changes invalidate them. A stale draft must be explicitly saved again to use current wording. Visual changes cannot alter parties, amounts or legal terms.

`contract_legal_snapshots` stores the document, resolved clauses, exact wording ids/versions, visual id/version/settings/renderer version, content hash and exception review. Existing party, office, asset and attachment snapshots remain authoritative. Logos are embedded as snapshot bytes. Issued text and HTML are exported from stored content, never regenerated from live office/asset/person/template data. Database triggers protect issued contracts and all associated snapshots.

**مراجعة العقود** lists drafts, issued contracts and cancellations. Each `/contracts/:id/review` page provides preview, information, legal conditions and action history tabs. Primary issue/edit/print actions remain visible; exports are secondary menu actions. The shared A4 preview supports zoom. Issued content is immutable, and legal-template deletion cannot change saved contract wording.

The cancellation action requires a reason, cancellation date and actor. One transaction changes only cancellation metadata and status, then appends audit evidence. It keeps all payments, attachments and snapshots, blocks repeat cancellation and later edits, and preserves property/rental availability because another contract or occupancy may exist. The cancelled document is displayed/exported with an archival cancellation mark; the underlying original bytes remain unchanged. Cancellation is an administrative record and does not claim to undo external legal procedures. Paid balances require a separate documented financial settlement/refund/remaining obligation action; cancellation never removes or reverses them automatically. `POST /contracts/:id/settlements` is protected by `contracts.cancel` and records refund, retained amounts or remaining obligations with a reference, date, reason and actor. Amounts are bounded and the request is idempotent. Settlement audit evidence remains separate from the immutable original financial amounts; it cannot silently rewrite or delete the original payment record.

Print/PDF/Word requests are recorded with the user; the audit records a requested output, not successful physical printing. Desktop printing uses the actual Electron print IPC and PDF export uses `printToPDF`; the browser adapter prints a sandboxed iframe and its PDF fallback downloads printable HTML. Draft output carries a draft label and cancelled output a cancellation label.

## Practical agreement data and follow-up

New documents are titled **اتفاق بيع عقار** or **اتفاق إيجار عقار**. Office name, logo, owner, address, phones, role and stamp/signature area are derived from office data and frozen at issuance. The office is the broker by default; an explicit contextual seller/buyer/lessor/lessee capacity can be recorded, with that party still selected in the agreement. Roles never move into `Person`.

The integrated creation page reuses `PersonEditor` to add or complete both parties. It validates full names (at least four name components for individuals), identity numbers, phone characters/length, governorate/district/neighborhood, residence-card numbers and selected applicable identity/residence documents. National or civil identity documents are accepted. A contextual switch requires both identity sides when needed; uploads can record front, back or both. Missing structured residential fields in old customer records need completion for new agreements only. Identity numbers are resolved from the appropriate document type, never an arbitrary attachment. Images remain managed private attachments; only their identifying metadata is printed.

Property descriptions, locations, plot/district details, area/unit, available deed information and intended rental use are read from actual data. No missing ownership details, dates, responsibilities or security approvals are invented. `agreement_details` captures payment terms, transfer target, handover/occupancy conditions, utility responsibilities, witnesses and available police/security references. The rental-procedure note is configurable. Rental start/end dates are required. Agreed periodic rent and advance/remaining amounts preserve the existing rental pricing semantics.

Printed office agreements omit empty optional facts and internal wording/visual version labels. Those versions remain in the immutable snapshot and management history. Both parties are clearly labelled as the first and second party, with their contextual roles.

Each saved agreement has independent sale/rental procedure steps with dates, references, notes, private supporting attachments and audit events. Displayed states distinguish draft, issued but signature unrecorded, signed and recorded completion of required procedures. Later procedures never block saving or printing. A completed step needs a valid non-future date; official steps need references; ownership transfer requires recorded registration and signing. Notarization never marks registration complete. Optional local rental requirements can be explicitly marked not applicable. Concurrent updates require the last timestamp. Editing follow-up does not modify the issued text, HTML, financial or party snapshots. The printed initial agreement provides blank follow-up lines, rather than suggesting any step already happened.

The sale explanation and conditional rental note use the exact wording supplied in the request. Registration is kept separate from the office document; the Iraqi Ministry of Justice describes the remit of the [General Directorate of Real Estate Registration](https://moj.gov.iq/tashkelat.7/). Local rental requirements are recorded when applicable, without claiming a universal security-approval requirement.

## Migration and verification

Apply `pnpm db:migrate`. Migration `0019_contract_legal_visual_separation.sql` retains legacy visual text and issued content. Additive migration `0020_legal_content_workflow.sql` adds workflow/provenance/scheduling fields and notices, preserves specialist approvals, and activates only the newest existing approved revision per exact scope. It approves no drafts and deletes no contract data. Migration `0021_office_agreements.sql` is additive: customer residential fields, document sides, office owner snapshots, agreement details, wording provenance, procedure records/files and necessary role permissions. It changes no issued agreement, attachment or user wording. Migration `0022_contract_management.sql` adds issuance/cancellation audit metadata, template protection/soft deletion and permission keys. It replaces lawyer-dependent approval/issuance triggers with office approval guards, supports only a documented cancellation transition for issued rows, and consolidates selected defaults per contract type. Existing wording, attachments, financial data and snapshots are retained. Reviewer qualification APIs are removed; the compatible legal approval workflow now uses account permissions. `approve` records approval; `approve_publish` or `publish` activates wording.

Full/CRM backups include all legal/visual history, deadlines, notices, procedure dates and supporting files, with date conversion, deferred self-references and serial restoration. Privileged restore bypasses guards only inside its transaction. Backups predating legal separation are rejected before replacing current legal history and should be migrated separately. Backups from before workflow fields default to unpublished upon restore, requiring an explicit activation.

`pnpm --filter @dalaly/server test:contracts` uses an isolated temporary PostgreSQL database. It verifies migrations and legacy preservation, all 12 visual equivalence, scope/conditions/optional clauses, office approval without any lawyer credential, manager/employee API permission guards, database immutability, routine issuance, optional recorded review, restoration, notice deduplication and full backup round-trip. Identity/address checks, both-side identity requirements and official procedure ordering remain covered.
