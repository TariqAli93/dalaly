# Central legal wording and contract issuance

Contract data, legal wording and visual design remain separate. `contract_templates` contains visual settings only (`body={{document}}`); its existing ids are preserved. Six sale and six rental designs consume the same structured document through `renderVisual`. People stay reusable; party roles belong to each contract. Rental assets and images remain separate from sale properties.

## Approval and publication

Every edit appends a complete revision to the existing `legal_contract_templates` / `legal_contract_clauses` tables. Wording, ordering, scope, legal references and approval evidence cannot be overwritten. `legal_content_events` records the actor, reason, parent, reviewed baseline, classification, specialist qualification when needed, publication and scheduling changes.

The displayed states are draft, ready for approval, specialist review needed, approved, active and archived. Existing `approval_status` values remain compatible; `publication_status` distinguishes approval from activation. Only an approved **active** version can serve new contracts. Activation atomically archives the previous active version in exactly the same contract/property/jurisdiction/transaction scope. A partial unique index prevents two active choices in that scope. The active version is the default for that exact scope, never for another property category.

The server compares actual wording with the latest approved revision in the same scope. Unicode NFC and whitespace are normalized; Arabic letters, terms and obligations are not rewritten. Clause codes, titles, required flags, conditions and effective order are part of the comparison. Metadata such as the template title, deadline and priority are administrative. Dynamic contract values are separate data and do not revise the wording.

- An administrative revision that retains the approved terms can be approved and published by the office manager directly, including from draft.
- New wording, changed scope, changed legal references or substantive clause changes require submission and an active qualified specialist before approval. Priority and deadlines never relax this check.
- The database independently compares stored terms at approval. A client classification or imported approval flag cannot establish approval. If the reviewed baseline changes while a draft is pending, administrative approval requires a new revision and comparison.
- Restoring an old version creates a new draft and compares it with the latest reviewed terms. It does not reset history or assume an old text is still appropriate.

No legal language or professional credentials are automatically approved. Historical text from before separation is retained for review; starting legal drafts remain empty until the office supplies reviewed wording. Credential evidence records human verification rather than claiming to check an external professional registry. No laws, obligations or exceptions are inferred from urgency or from a visual design.

## Permissions

`legal_content.read` permits viewing active wording and previewing it. `legal_content.propose` lets employees create revisions and submit proposals without publication. `legal_content.manage` permits management and scheduling. `legal_content.publish` allows administrative approval, activation/deactivation and default selection. `legal_content.approve` is the exceptional specialist authority and additionally requires an active verified `legal_reviewers` record for an active account. `legal_reviewers.manage` manages qualification evidence. Permissions are enforced by the API as well as reflected in the UI.

The migration adds unassigned `office_manager` and `legal_editor` roles. Office managers receive legal management/publication and existing contract/design management permissions; employees receive read/propose. Existing admin and Super Admin roles receive administrative publication. Existing Super Admin permission behavior is preserved, but specialist eligibility still requires recorded human verification.

## Editor, clauses and follow-up

**الإعدادات ← إدارة الصيغ القانونية** has four statistics, Rental/Sales/Clauses/Versions tabs, searchable property/state tables and permission-aware actions. The editor has metadata and ordered clauses on the right, and the shared RTL A4 preview on the left. Reviewed terms are locked by default. Opening them for changes marks the edit for comparison; the server makes the final classification.

Preview uses all six visuals for the chosen domain and either explicitly labelled demo values or saved real-contract data. It is always marked as an editor draft. Real data must match contract type, property category, jurisdiction and transaction kind. Optional clauses are shown for inspecting the formula; actual contracts still choose only applicable approved optional clauses. Trial free conditions in the editor affect preview only. No script, HTML, SQL or arbitrary variable evaluation is accepted.

The shared variable whitelist rejects unknown or malformed placeholders. Duplicate normalized clause text is reported before approval; no historical legal terms are deleted automatically. The clause library groups identical reviewed terms and reuses their provenance. Revision snapshots deliberately retain their own clause copies so future library changes cannot alter history. JSON import opens a draft in the editor and ignores external approval/publication flags; JSON export excludes local clause references for transfer to another installation.

Requests have a Baghdad-time target and priority. Submission assigns a one-day operational target if none was supplied; specialists/managers can adjust it to the nature of the work. These are operational goals, not legal deadlines. The dashboard groups similar pending requests and shows remaining/overdue time. In-app notices are generated on access and refreshed every minute while the app is open. They are deduplicated per user/revision/target/kind: at most an early and an overdue notice for an unchanged target. Read state persists, obsolete/resolved notices disappear, and optional Electron desktop notices group new items with local suppression and rate limiting. The app does not run a background notification service while closed.

The layout uses existing Vuetify controls, Dalaly colors and RTL. Spacing, grouping and progressive disclosure follow the [Fluent 2 layout guidance](https://fluent2.microsoft.design/layout) using the existing 4-pixel spacing system; no second UI framework is added. Windows desktop notices use the app's AppUserModelID; development notification display also depends on Windows shortcut/OS settings as described in [Electron's notification guidance](https://www.electronjs.org/docs/latest/tutorial/notifications#platform-considerations).

## Contract integration and historical records

Selection requires exact contract type, canonical property type, jurisdiction and transaction kind. There is no wildcard or residential fallback. Sale Arabic categories and rental keys are preserved; office and unspecified rental land are additive categories. Agricultural land retains metre/dunam data. An already-approved version remains usable while a new proposal is pending if the manager keeps it active.

Routine contracts using active approved wording issue through `contracts.manage` without an independent daily specialist review. Free additional conditions require a review tied to the saved content hash and active specialist eligibility. Changes invalidate that review. Issuance verifies that the saved wording versions are still active; a stale draft must be explicitly prepared again. Changing its visual design cannot change its legal model, parties or amounts.

`contract_legal_snapshots` stores the document, resolved clauses, exact wording ids/versions, visual id/version/settings/renderer version, content hash and exception review. Existing party, office, asset and attachment snapshots remain authoritative. Logos are embedded as snapshot bytes. Issued text and HTML are exported from stored content, never regenerated from live office/asset/person/template data. Database triggers protect issued contracts and all associated snapshots.

The saved-contract toolbar provides PDF/Word export, optional exception review and issuance above the scrolling document. Unready drafts remain exportable with a draft label. The matching legal page provides a return link; explicitly preparing and saving a draft uses current active wording and preserves payment metadata. Desktop export uses Electron's real `printToPDF` and native save dialog. Browser/demo export downloads printable HTML and explains browser print-to-PDF.

## Migration and verification

Apply `pnpm db:migrate`. Migration `0019_contract_legal_visual_separation.sql` retains legacy visual text and issued content. Additive migration `0020_legal_content_workflow.sql` adds workflow/provenance/scheduling fields and notices, preserves specialist approvals, and activates only the newest existing approved revision per exact scope. It approves no drafts and deletes no contract data. Historical contracts are unchanged. No existing API payload fields are removed; behavioral change: `approve` alone records approval, while `approve_publish` or `publish` explicitly activates wording for new contracts.

Full/CRM backups include all legal/visual history, deadlines and notices, with date conversion, deferred self-references and serial restoration. Privileged restore bypasses guards only inside its transaction. Backups predating legal separation are rejected before replacing current legal history and should be migrated separately. Backups from before workflow fields default to unpublished upon restore, requiring an explicit activation.

`pnpm --filter @dalaly/server test:contracts` uses a new temporary PostgreSQL database and verifies migration/legacy preservation, all 12 visual equivalence, scope/conditions/optional clauses, administrative versus substantive classification, manager/employee permissions, direct database tampering, routine issuance, reviewed exceptions, immutable histories, restoration, notification deduplication and full backup round-trip. `test:contracts:browser` additionally exercises editor previews with real data across all six designs, administrative publishing, comparison/restoration/import, substantive-review controls, notification read state, activation/deactivation, visual editing, small-viewport exports, direct routine issuance, exception review, and all twelve Arabic A4 PDFs. An isolated hidden Electron harness uses the actual preload and production PDF/notification IPC modules: it creates another twelve real A4 PDFs, checks cancellation/invalid input, and tests notification delivery/rate limiting with OS display intercepted. Native save dialogs and actual OS toast display are not automated. Test credentials, approvals and wording never enter the application database.
